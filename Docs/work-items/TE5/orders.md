# Orders - TE5

Common constraints: no change to application code or to the existing stages' results (the 404 existing checks keep passing unchanged); pinned versions for Playwright, axe-core and browser builds; no secrets in the repository (test administrator credentials come from the same environment the existing runtime tests use); never log tokens, passwords or message bodies; the browser tests run against the live stack inside the verification container and write results in the same per-test line format as the other stages so `verify-results/latest.json` and the summary count them; tests are deterministic (no sleeps on wall-clock, wait on conditions); a defect found by a test is reported through the known-issues mechanism below and is never silently skipped.

## O1 - Browser test layer and stage (serves TE5-AC1, AC7)
Target: `verify/browser/` (new Node project: package.json, lockfile, Playwright config with Chromium, Firefox and WebKit projects, helpers: base URL and certificate handling for the Caddy HTTPS stack, signed-in administrator session using the seeded test administrator, console and request error collector, the screen list), `Dockerfile.verify` (install the pinned browsers and their system dependencies), `verify/stages/40-browser.sh` (run the tests, emit one `PASS`/`FAIL`/`KNOWN` line per test per browser in the existing log format and into the JSON), `scripts/verify.ps1` and `verify/lib.sh` only as needed, `Docs/tests/README.md` and `Docs/architecture.md` section 10 (how to run all, run one browser, add a test, read a failure). Include the known-issues mechanism: `verify/browser/known-issues.json` entries {id, screen, kind, description, fixedBy}; a matching defect is reported `KNOWN` (counted separately from pass and fail in the summary); an entry that no longer reproduces makes the test fail with "remove this known issue". Include a smoke test proving the layer works end to end (home page loads on all three engines).

## O2 - The checks (serves TE5-AC2 to AC6)
Target: `verify/browser/tests/`. Tests for each screen in the screen list (home, sign-in, email confirmation without a token, contact confirmation without a token, access denied, and with the administrator: editor workspace, new story form, new project form): loads with no failed request and no uncaught console error (AC2); axe-core WCAG 2.1 A and AA with the test failing on any critical or serious violation and logging every violation (AC3); 320 px `scrollWidth <= 320` (AC4); keyboard: tab through from the top, every interactive element is reached in page order and every focused element has a visible focus indicator (AC5); reduced motion on the home page: emulate `prefers-reduced-motion: reduce` and assert no running animations or transitions, including inside the `<gcv-scene>` shadow root, and that the page content is present (AC6). Run them, record real findings in `known-issues.json` with `fixedBy: "F9-US7"`, and list the findings in the change record with their evidence.

## O3 - Tighten the checks (serves TE5-AC3 to AC6; from the Reviewer advisories on O1 and O2)
Target: `verify/browser/` and `verify/stages/40-browser.sh`, `Docs/architecture.md` section 10. Each item test-first with a negative control that you show failing and then remove or keep as a self-test: (1) keyboard focus indicator compared against the unfocused state (the indicator must be a change, not an always-present decoration); (2) the reachable-element selector also covers `[role=button|link|checkbox|tab|menuitem]` with tabindex, `[tabindex]` elements, `summary`, `[contenteditable]`, `iframe` and media with `controls`, and the keyboard check is also run at a 320 px viewport on the home page with the mobile menu opened (the menu button and its links reachable by keyboard); (3) known axe entries identify the element target as well as the rule, so a later entry cannot mask a different element; (4) a known-issues entry whose `screen` or `kind` matches no test fails the stage ("orphan known issue"); (5) the 320 px test asserts the real viewport width (`innerWidth` 320) before measuring; (6) `40-browser.sh` counts its own failures instead of the global FAIL counter and fails if the number of results differs from the expected count (screens x checks x engines, computed from the test list), so a crash that drops tests cannot pass; (8) update the stale "Current result" line in `Docs/architecture.md` section 10 to the real current totals after your final full run. Advisory 7 (late requests after `networkidle`) is recorded as a known limit in the docs, not changed. Constraints as in the Common constraints; run `./scripts/verify.ps1 -SkipCi` once at the end and report totals (pass/fail/known) and three identical stage-only runs.
